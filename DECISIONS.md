# Decisions

Decisions that change or add to `spec.md`. Newest last.

| # | Date | Decision | Why |
|---|------|----------|-----|
| D1 | 2026-10-28 | Versions pinned: Spring Boot 4.1.2, Spring AI 2.0.2, Maven 3.10.0 via wrapper 3.3.4 (distribution SHA-256 pinned). Library versions come from the Boot and Spring AI BOMs and are not overridden. | Latest patch releases on Maven Central at project start; Spring AI 2.0.0 was built on Boot 4.1. |
| D2 | 2026-10-28 | Java package and groupId: `dev.spasbo.aigateway` / `dev.spasbo`. | Not specified in the spec. |
| D3 | 2026-10-28 | JaCoCo gate: 90% LINE and BRANCH covered ratio over the whole bundle, Surefire and Failsafe feeding one agent, checked in `verify`. The only exclusion is `AiGatewayApplication` (its `main` is never invoked by `@SpringBootTest`). `-Dcoverage.minimum` raises it later. | Spec asks for 90/90 to start; excluding bootstrap code avoids a test that starts and leaks a full application. |
| D4 | 2026-10-28 | Milestone 1 runs only infrastructure in Compose (Postgres, Keycloak, Ollama + a one-shot model pull); the gateway runs on the host with `./mvnw spring-boot:run`. Postgres is published on host port 5433 by default. | Running the app in Compose makes token issuers differ (`localhost:8180` vs `keycloak:8080`), which is solvable but teaches nothing for M1. 5433 avoids clashing with a locally installed Postgres. |
| D5 | 2026-10-28 | M1 creates only the four tables F1 writes to (tenant, app_user, usage_record, audit_event); the rest arrive with their milestones. usage_record and audit_event reference app_user by the composite (tenant_id, user_id), so a row can never pair a user with another tenant. Status/outcome are `SUCCESS` or `ERROR`; `app_user` is unique on (tenant_id, external_subject). | Schema grows with features; the composite key makes tenant consistency a database guarantee, not a convention. |
| D6 | 2026-10-28 | The local dev tenant (`7f3c1e2a-5b8d-4c6e-9a0f-3d2b1c4e5f60`, "Local Dev Agency", 1,000,000 tokens/month) is a repeatable Flyway migration in `db/local`, added to `spring.flyway.locations` only by the `local` profile. | A versioned migration in a second location would cause out-of-order errors once later `V` migrations are added. |
| D7 | 2026-10-28 | Keycloak realm `ai-gateway` (`keycloak/ai-gateway-realm.json`, imported by Compose and by the Keycloak Testcontainer). DEV ONLY: public client `ai-gateway-cli` with direct access grants for curl; users `alice` (user), `ada-admin` (user+admin), `orphan` (tenant not seeded, for the 403 path), passwords `<username>-dev-only`. Tokens carry `tenant_id` (user attribute, admin-editable only in the declarative user profile), `roles` (realm roles) and audience `ai-gateway-api`. | Spec puts tenant and roles in the JWT but does not name claims; an audience lets the gateway reject tokens minted for other clients. |
| D8 | 2026-10-28 | `/api/**` requires ROLE_USER or ROLE_ADMIN, mapped from the `roles` claim; unknown Keycloak roles (`offline_access`, `default-roles-*`) are ignored, and a token with no gateway role gets 403. A user holding both roles is stored in `app_user.role` as ADMIN. Everything outside `/api/**` is denied. | `app_user.role` is a single value; deny-by-default keeps new endpoints closed until deliberately opened. |
| D9 | 2026-10-28 | A missing, malformed (non-UUID) or unknown `tenant_id` all return the same 403 problem detail ("Tenant not recognized"); the specific reason is logged, not returned. Tenant resolution runs as a filter after Spring Security's authorization filter and reports errors through the MVC exception resolver. | Spec only defines unknown → 403; one response avoids telling a caller which tenant IDs exist. |
| D10 | 2026-10-28 | The model allowlist is config (`gateway.models: [{id, provider}]`), validated at startup (non-empty, no duplicate ids). `GET /api/models` ships in M1 and returns that list. M1 has one provider (Ollama); provider routing by model id is M3. | The spec lists `/api/models` without a milestone; it is trivial once the allowlist exists. |
| D11 | 2026-10-28 | Usage and audit rows are written together in one short transaction **after** the model call returns, never inside a transaction around it. Audit `action` is `CHAT`; `prompt_text` is always null in M1. Token counts come only from the provider's `Usage`; a missing count is stored as 0, never estimated. | A model call can take seconds; holding a pooled connection for its duration would exhaust the pool under load. |
| D12 | 2026-10-28 | In M1 any exception from the model call, or a response with no generation, becomes a 502 "Model provider error" problem detail carrying only the model id; the cause is logged server-side. Telling throttling/timeouts/5xx apart is M3 (F3, WireMock contract tests). | Spec: a provider failure returns a clear 502, not a stack trace; provider hostnames and error text are internal details. |
